How it works

One process, six stages, nothing on the fill path touches HTTP

A fill is a sequencer frame decoded before the block is queryable, a launch confirmed by log, up to ninety seconds of tape, a score, the guards, a real buy-then-sell simulation, and a raw transaction broadcast to every RPC in parallel.

1

Intake

The sequencer feed is decoded roughly 100 to 300 ms before a block is queryable. Factory calldata is matched on the frame, and the launch is confirmed by its log before anything else happens.

2

Observation window

Up to ninety seconds of tape after first sight: unique buyers, volume, concentration, deployer behaviour, bundling, timing entropy. An arm chooses how much of the window to wait through.

3

Oracle

A bucketed logistic model with three heads scores the snapshot 0 to 100 and tiers it. Rug risk is published beside the score, never blended in. Every verdict quotes the buckets that moved it.

4

Guardrails

An ordered risk engine runs the cheapest, most fatal check first and fails closed on anything it cannot read. A refusal is journaled with its reason in plain language.

5

Execution

A real buy-then-sell simulation runs before every live buy. A token that can be bought but not sold is blocked. The pre-built swap is broadcast raw to every RPC at once.

6

Learning loop

Labels resolve 24 hours later and are price-independent. Every six hours a candidate is fitted on a time-split holdout and promoted only through a gate it can fail.

The oracle

A score is a probability claim, and the gate checks the claim

The 0 to 100 ladder is a public contract. Each rung claims a minimum P(win); what moves across refits is the weight behind the rungs, never the number on the pill.

Tiers and what they claim

Only prime and strong are act signals. A conviction engine that likes everything is a hype engine.

prime86+P(win) at least 45%
strong72+P(win) at least 25%
lean56+P(win) at least 12%
watch34+P(win) at least 5%
avoid0+below that

Three heads, not one

"This will probably run" and "this will probably take your money" are different questions. One number that averages them answers neither.

win
Did it run (2x from first sight) and is a first-sight holder still up? The published score anchors here.
rug
Is a first-sight holder down more than half? Published as its own number on every verdict and gated per arm.
moon
Did it run at all, whatever happened next? Kept so fits stay comparable and to show give-back risk.

Features, in four pillars

29 EVM-native feature definitions measured over the ninety-second window; the banner above says how many the active model weighs. Bucketed, not sloped, because several are genuinely non-monotone.

structureorganic share, bundling, snipe ratio, coordination, timing entropy, holder concentration, fresh wallets, funder connectivity
momentumunique buyers and sellers, buy/sell ratio, volumes in ETH, trade count, largest and typical buy, market cap at first sight
pedigreedeployer buys and sells, deployer still holding, smart-money presence, creator record
narrativeclassified category and how confident the classifier was

Labels that cannot drift with the price of ETH

Labels resolve 24 hours after first sight as ratios of two readings of the same market cap, so the price of ETH cancels out.

retained      = last_market_cap / ath_market_cap
hold_multiple = ath_multiple * retained

moon = graduated OR ath_multiple >= 2
rug  = NOT graduated AND hold_multiple <= 0.5
win  = moon AND hold_multiple >= 1

A position the engine actually closed overrides the chart label for that token. What we got out is a better teacher than what a chart says a holder could have got.

The promotion gate

Every six hours a candidate is fitted and judged. It replaces the live model only when all of these hold; a losing candidate is archived with the reason.

  • fit_complete the fit reached its last epoch
  • absolute_auc win holdout AUC at least 0.70
  • tier_honesty every populated tier band observes at least 70% of the probability it claims
  • feature_set no collapse of the feature set against the incumbent
  • no_regression_rug / no_regression_moon neither other head regressed beyond 0.01 AUC
  • auc_gain beats the incumbent by more than 0.004 AUC, the noise floor between two fits

Guardrails

Fourteen checks, in order, and every one fails closed

Cheapest and most fatal first, so the journaled reason is the most meaningful one. Sells are exempt from the exposure caps, because a cap must never trap a losing position, and still honor the kill switch, cooldown and slippage bound.

Guardrails doc
  1. kill_switchGlobal kill switchTripped by SIGINT or SIGTERM, a KILL file, GLOBAL_KILL=1, or POST /api/kill. Halts new risk. Never sells on its own.
  2. zero_amountAmountThe order is 0 wei.
  3. slippage_boundSlippage boundThe order's slippage exceeds the arm's slippageBps.
  4. cooldownCooldownLess than cooldownSeconds since this arm's last trade. Applies to sells too.
  5. disarmedArm stateThe arm is disabled or its own kill switch is set.
  6. concurrencyConcurrencymaxConcurrentPositions are already open.
  7. per_trade_capPer-trade capThe buy exceeds perTradeWei, or the cap is 0.
  8. daily_budgetDaily budgetRolling 24h spend plus this buy exceeds dailyBudgetWei, or the budget is 0.
  9. daily_lossDaily loss breakerRealized 24h loss reaches half the daily budget.
  10. wallet_floorWallet floorThe balance could not be read, or the buy would leave less than MIN_WALLET_ETH plus 0.001 ETH gas headroom.
  11. price_impactPrice impactThe quote has no impact figure, or impact exceeds maxPriceImpactPct. Unknown depth is refused, not assumed.
  12. firewallFirewallA real simulated buy-then-sell round trip fails or loses too much.
  13. oracle_gateOracle gateScore below minOracleScore or rug risk above maxRugRisk.
  14. entry_filterEntry filtersAny structural, pedigree or narrative filter on the arm: buyers, creator record, deployer holding, bundle score, concentration, market-cap band, socials, dev dump, category.

The kill switch philosophy

A kill halts new risk. It never market-sells, unwinds or cancels anything on its own: a forced exit into thin launch liquidity during whatever caused the panic is usually worse than holding. Exits keep managing while killed. Only an API kill is clearable at runtime; a file, signal or environment kill is cleared where it was set.

Earned autonomy

An arm's realized live record sets its tier, and the tier bounds what the optimizer may change and how far. Trusted needs a net edge of at least +0.5% over 12 closed live trades with drawdown under 35%; autonomous needs +5% over 40 with drawdown under 25%. No tier can touch the kill switch, wallet floor, loss breaker, impact ceiling, concurrency, slippage or firewall, and every tier keeps a stop loss.

On-chain arms

The same guardrails, enforced by the chain, with your keys

Server-side guardrails protect you from a bad market. They do not protect you from the server. The arm contracts in contracts/ move the caps into a per-user managed account on Robinhood Chain, so the engine can trade for you without ever holding your funds.

in development

A managed account per user

You deploy your own account, deposit ETH, and name the engine's hot key as operator. The operator can only call the trade functions; the owner can withdraw at any time, positions open or not.

Caps the operator cannot cross

Per-trade cap, daily budget, cooldown and concurrency live in the account's policy and revert on breach. Every revert carries the numbers a human needs: PerTradeCap(amountWei, capWei), DailyBudget(wouldSpendWei, budgetWei), Cooldown(remainingSeconds).

Allowed router and slippage bound

Trades route only through the router the policy names, and the caller's amountOutMinimum must satisfy the policy's slippage bound against the pool's current price. A router swap is refused with RouterNotAllowed.

Oracle-score gate

A policy can require a fresh, signed oracle attestation above a minimum score before the account will buy a token. Stale or expired attestations are refused. The attestation is a plain signed struct so that other contracts can consume it too.

Kill switch and timelock

The owner trips the kill switch and every new buy reverts with KillSwitch(). A change that loosens the policy queues behind a timelock; a change that tightens it applies at once.

Fees at the contract level

A performance fee accrues only on realized profit and is capped by the protocol at 20%, split through an on-chain splitter. There is no fee on deposits, losses or withdrawals.

The revert names mirror the RefusalReason vocabulary the off-chain risk engine already journals, so the dashboard maps a revert selector straight onto the reason you already know. Security model and threat analysis: the litepaper.

For agents

The oracle is a service other agents can call

Every read is public JSON. The agent surfaces put the same scorer behind MCP tools, a typed client and a paid endpoint, so an autonomous trader on Robinhood Chain can buy conviction instead of building it.

MCP

MCP server

The oracle feed, a launch's full read, arm management, position closes and the kill switch as Model Context Protocol tools, over stdio (npx hood-oracle-mcp) or Streamable HTTP inside the engine (/mcp). Reads are free; writes need the operator token. MCP doc

SDK

Typed client

@hood-oracle/sdk: a typed client for every route, an async iterator over the SSE streams, a waitForScore helper, and an x402 helper that pays for a score. Its wire types are generated from the server's contract, so a renamed field fails your build instead of rendering undefined. SDK doc

x402

Pay-per-score

GET /api/x402/score/:token answers 402 until the request carries a signed USDG payment on Robinhood Chain, then returns the verdict, the feature snapshot and the firewall round trip. The price is published at /api/x402/pricing. No account, no key, no gas for the buyer. x402 doc

# the public reads work today, no token needed; HOOD is your engine's base URL
export HOOD=http://localhost:8080
curl -s "$HOOD/api/oracle/feed?tier=strong&limit=5"
curl -s "$HOOD/api/oracle/model"
curl -N "$HOOD/api/oracle/stream"   # SSE: launch, features, score

Open source

Apache-2.0, one container, your Postgres

The engine, the API, the dashboard and this site are one Node 24 process. Run it locally against Docker Postgres in a few minutes; simulate mode is on by default and signs nothing.

github.com/nirholas/hood-oracle 
git clone https://github.com/nirholas/hood-oracle.git
cd hood-oracle
cp .env.example .env
docker compose up -d db         # Postgres 17 on localhost:5432
npm install
npm run db:migrate
npm run oracle:backfill -- --days 30
npm run dev                     # http://localhost:8080
